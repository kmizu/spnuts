# SPnuts 0.1.0 Release and GitHub Pages Distribution

Date: 2026-07-26
Status: Approved for autonomous implementation under the active release goal

## Goal

Publish SPnuts 0.1.0 as a usable release.  GitHub Pages must contain both the
release documentation and the actual downloadable, integrity-checked artifacts.

## Release contract

The release workflow runs for a pushed `v*` tag and can be started manually
with an explicit version.  It derives the version from the tag (or the manual
input), rejects a mismatch with `build.sbt`, and creates these assets from one
Ubuntu build:

- `spnuts-<version>-jvm.tar.gz`: a self-contained JVM REPL distribution with a
  POSIX `bin/spnuts` launcher and every runtime JAR in `lib/`.
- `spnuts-<version>-linux-x86_64.tar.gz`: a Scala Native REPL distribution with
  a POSIX `bin/spnuts` executable.
- `SHA256SUMS`: SHA-256 checksums for both archives.

The workflow uploads exactly those assets to the GitHub Release and deploys
the same files to `downloads/` on the Pages site.  This makes the web site and
the release mutually consistent rather than relying on hand-maintained links.

## Site contract

The source documentation lives in `site/` and is converted into the Pages
artifact by a repository-owned packaging script.  The published site contains:

- a version-labelled landing page and direct links to both archives;
- prerequisites, install/run instructions, a script example, and checksum
  verification;
- platform/feature notes that distinguish JVM and Native behavior;
- a release manifest used by the landing page and humans to inspect the
  generated version and file names.

No third-party site generator is introduced.  Keeping the site static and
plain HTML/CSS means the Pages artifact can be validated locally with only
the POSIX tooling already available in GitHub Actions.

## Build and deployment design

`scripts/package-release.sh` accepts a version and output directory.  It runs
the existing sbt tasks, obtains the JVM runtime classpath through sbt, copies
the resolved JARs into the JVM package, creates the launcher, links the Native
binary, stages both distributions, and writes `SHA256SUMS`.

`scripts/build-pages.sh` accepts the same version, the release-artifact
directory, and a Pages staging directory.  It copies `site/`, fills its
version/download placeholders, copies the archives plus `SHA256SUMS` into
`downloads/`, and emits `downloads/manifest.json`.  The script validates that
all required source and artifact files exist before writing output.

`.github/workflows/release.yml` has a `build` job that tests the JVM projects,
packages both distributions, verifies each archive and checksum, and uploads
one workflow artifact.  Its `release` and `pages` jobs consume that exact
workflow artifact.  Pages uses GitHub's official `upload-pages-artifact` and
`deploy-pages` actions; release assets are created through the GitHub CLI.

The release notes and site acknowledge this as the first Scala reimplementation
release after Toyokazu Tomatsu entrusted the continuation of Pnuts to the
project maintainer. This is historical context, not an endorsement claim or a
change to the original license.

## Non-goals

- Publishing Maven artifacts is out of scope for 0.1.0; the release contract is
  runnable distributions for end users.
- macOS and Windows Native binaries are not claimed from the Linux release
  build.  The JVM archive remains portable anywhere a supported Java runtime
  exists.
- The release does not change SPnuts language syntax or semantics.

## Verification

Local release verification must prove: JVM tests pass, both archives contain
their documented launch targets, the JVM launcher evaluates a script, the
Native executable evaluates a script, checksum verification succeeds, and the
Pages staging result contains documentation plus byte-identical downloadable
assets.  The GitHub workflow repeats the portable build checks and validates
the Pages artifact before deployment.
