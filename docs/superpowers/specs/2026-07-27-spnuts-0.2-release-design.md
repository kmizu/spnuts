# SPnuts 0.2.0 Release Design

Date: 2026-07-27
Status: Approved for autonomous implementation under the active `v0.2.0` goal

## Goal

Publish SPnuts 0.2.0 from the current `main` branch. The release is centered
on mandatory gradual typing and must ship runnable, integrity-checked JVM and
Linux Native distributions through both GitHub Releases and GitHub Pages.

## Scope

SPnuts 0.2.0 contains the language and runtime state already merged to
`main`, including mandatory gradual typing. The release preparation does not
add another language feature or redesign the distribution format.

The release changes:

- the project, REPL banner, and user-facing download version to `0.2.0`;
- English and Japanese release-facing documentation;
- the Pages landing page's release highlight;
- release contract tests and packaged-distribution smoke coverage;
- the release workflow's test gate, so shared JVM/Native typing semantics are
  tested before publishing;
- curated release notes stored at `docs/releases/0.2.0.md`.

## Alternatives considered

### Version-only cut

Only update version strings and rely on automatically generated GitHub notes.
This is the smallest change, but it does not explain the compatibility impact
of fixed inferred types and does not prove the new typing contract in packaged
artifacts.

### Release-focused cut (selected)

Keep the existing asset and Pages architecture, add curated user-facing notes,
and strengthen release smoke tests around mandatory typing. This gives users a
clear migration story without introducing unrelated product work.

### Release-system redesign

Derive versions dynamically from Git tags or replace the current packaging
workflow. The existing tag/version validation and shared artifact flow already
worked for 0.1.0, so this adds risk without helping the 0.2.0 outcome.

## Version and documentation contract

The following sources must agree on `0.2.0`:

- `ThisBuild / version` in `build.sbt`;
- the startup banner in `repl/shared/src/main/scala/spnuts/repl/Repl.scala`;
- the English download heading and REPL transcript in `README.md`;
- the Japanese download heading in `README-ja.md`;
- the title and content of `docs/releases/0.2.0.md`.

The root READMEs continue to describe mandatory checking as unconditional.
The release notes call out the compatibility consequence explicitly: a script
that reassigns a binding to an incompatible type may have run under 0.1.0 but
is rejected before execution under 0.2.0.

## Release notes contract

`docs/releases/0.2.0.md` is the curated source for the GitHub Release body. It
contains:

- fixed inferred types for unannotated bindings;
- explicit annotations, generic functions, and structural compatibility;
- `Any` at dynamic Java, host, and `eval` boundaries;
- transactional pre-execution checking and source-positioned diagnostics;
- `Long -> Double` widening and primitive `null` protection;
- JVM/Native parity and platform limitations;
- the compatibility note for scripts that change a binding's type.

After the tag workflow creates the release, the controller updates the GitHub
Release body from this file and verifies the published body.

## Distribution and Pages contract

The existing asset names remain unchanged except for the version:

- `spnuts-0.2.0-jvm.tar.gz`;
- `spnuts-0.2.0-linux-x86_64.tar.gz`;
- `SHA256SUMS`.

The JVM archive remains portable with Java 17+. The Native archive remains
Linux x86_64. Java interoperation remains JVM-only.

The Pages build continues to copy the exact release archives and checksum file
into `downloads/`. The landing page is version-labelled and adds a "What's new"
section that explains mandatory gradual typing with a compact valid/error
example. The generated `manifest.json` reports `0.2.0`.

## Packaged runtime verification

Release verification exercises the installed launchers rather than only sbt
entry points.

For both JVM and Native packages, a valid script must:

1. infer `count` as `Long`;
2. update it with another `Long`;
3. print `2`.

An invalid complete script must:

1. contain output statements before and after an incompatible assignment;
2. report a source-positioned type error with expected `Long` and actual
   `String`;
3. print neither side-effect marker, proving the whole chunk was rejected
   before execution.

Both archives must contain their launchers and licenses, pass checksum
verification, and be byte-identical to the copies staged for Pages.

## Workflow and publication

The existing `.github/workflows/release.yml` remains tag-driven for `v*` tags
and manually dispatchable with an explicit version. It continues to reject a
tag/build version mismatch.

The build job runs the complete sbt test graph before packaging. This is
required because the headline feature lives in shared code and has JVM and
Native runtime boundaries. The workflow then builds one release bundle; the
GitHub Release and Pages jobs consume that same bundle.

Publication order:

1. merge the release preparation PR to `main` after CI is green;
2. create and push annotated tag `v0.2.0` at that merge commit;
3. wait for the tag-triggered Release workflow to complete;
4. replace generated release text with `docs/releases/0.2.0.md`;
5. verify the tag, release body, three assets, checksums, archive launchers,
   Pages deployment, version manifest, and byte identity where observable.

The tag is never moved after publication.

## Error handling and recovery

- Version disagreement fails locally before packaging and in the workflow.
- Missing archives, launchers, licenses, or Pages inputs fail contract tests.
- A packaged typing smoke mismatch fails before the tag is pushed.
- The tag is not created until the release PR and its CI are green.
- If the tag workflow fails for a transient external reason, rerun the same
  tagged workflow only after the cause is understood. A source or workflow
  defect requires an explicit follow-up release decision; do not silently
  move or recreate the published tag.
- Do not publish partial local artifacts manually as a substitute for a failed
  workflow.

## Non-goals

- Maven Central or another package repository.
- macOS or Windows Native binaries.
- A new language feature beyond the already merged gradual typing work.
- A redesign of version derivation or the release artifact format.
- Deleting the 0.1.0 release or its assets.

## Completion evidence

The objective is complete only when all of the following are authoritative
and current:

- the release preparation PR is merged into `main`;
- `v0.2.0` points at the intended `main` merge commit;
- the tag-triggered Release workflow completed successfully;
- GitHub Release `v0.2.0` is published with the curated notes;
- all three expected assets exist and `SHA256SUMS` verifies them;
- both packaged launchers passed the valid and invalid typing smoke tests;
- GitHub Pages displays 0.2.0 and its manifest names the same archives;
- the Pages downloads correspond to the release assets;
- no required check, asset, or documentation item remains pending.
